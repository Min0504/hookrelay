# HookRelay — 웹훅 딜리버리 플랫폼

> **포트폴리오 포지션: 3순위 (PointLedger 이후, 인프라·운영 역량 담당).**
> Stripe·GitHub·Toss Payments가 실제로 운영하는 "웹훅 배달"을 축소 구현하는 B2B 인프라 서비스.
> 앞 두 프로젝트가 "요청-응답 안의 정합성"이라면, 이 프로젝트는 **"응답 이후의 세계" — 큐, 재시도, 배달 보장, 관측(observability)** 을 다룬다.
> 서브 스택인 **NestJS(TypeScript)를 유지·심화**해 스타트업/글로벌 풀 보험을 지키면서, 인프라·SRE 지향 관심사를 정면으로 증명한다.

---

## 1. 프로젝트 기본 정보

| 항목 | 내용 |
|------|------|
| 프로젝트명 | HookRelay (훅릴레이) |
| 한 줄 설명 | 서비스에서 발생한 이벤트를 구독자의 HTTP endpoint로 **at-least-once 보장**으로 배달하는 웹훅 인프라 |
| 목적 | 메시지 큐·비동기 처리·재시도·DLQ·멱등 소비·모니터링 등 "분산 시스템 신뢰성" 문제를 실제 구현으로 증명 |
| 예상 사용자 | 웹훅 수신이 필요한 외부 개발사(테넌트) — B2B 개발자 대상 SaaS 가정 |
| 핵심 문제 | 수신자가 느리거나 죽어도 이벤트를 잃지 않기, 다른 테넌트에게 피해 전파 않기(noisy neighbor), 중복 배달의 안전한 처리 |
| 해결 방법 | Transactional Outbox + BullMQ(재시도·백오프·DLQ) + HMAC 서명 + 테넌트별 동시성 제한 + Prometheus/Grafana 관측 |
| 예상 개발 기간 | 6~8주 (주 15시간) |
| 난이도 | 중상 — 기능은 단순하나 "실패 시나리오"의 수가 많다 (실패가 곧 도메인인 프로젝트) |
| 핵심 역량 | **메시지 큐/비동기, 배달 보장, 장애 격리, 보안(HMAC·SSRF), 모니터링, 수평 확장** |
| 클라이언트 | **웹 개발자 콘솔** — Stripe 대시보드 모델. `frontend/` 폴더 분리, 판단 근거는 §3 |

### 언어 선택 근거

- **TypeScript 5(strict) + NestJS 11.** 전략상 서브 스택을 실전 수준으로 유지하는 프로젝트가 하나 필요하다 — Java 2개 + TS 1개 조합으로 "메인 깊이 + 서브 실무 가능"을 동시에 증명.
- 웹훅/이벤트 인프라는 Node 생태계(BullMQ)가 실제 업계에서 강한 영역이라 스택-도메인 정합성도 맞다.
- Todayskin(NestJS CRUD+AI 연동)과의 차별화: 같은 프레임워크지만 주제가 완전히 다르다 — 여기서는 HTTP 핸들러가 아니라 **워커·큐·프로세스 분리**가 주인공.

## 2. 핵심 기능 (기능마다 백엔드 문제 명시)

| 기능 | 내용 | 여기서 발생하는 백엔드 문제 |
|------|------|------------------------------|
| 테넌트 등록/API 키 | 테넌트 발급, 키 회전(rotate) | 키 해시 저장, 구 키 유예기간(grace period) |
| Endpoint 등록 | 수신 URL + 구독 이벤트 타입 + 시크릿 | **SSRF** — 내부망 URL 등록 차단, URL 검증 |
| 이벤트 발행 API | 테넌트가 `POST /events`로 이벤트 게시 | 발행 멱등성, **DB 저장과 큐 적재의 원자성(핵심)** |
| **배달 (delivery)** | 구독 endpoint로 HTTP POST + HMAC 서명 | 타임아웃, 5xx, 연결 거부 — 실패의 분류와 대응 |
| **재시도** | 지수 백오프+지터, 최대 8회 (총 ~13시간) | 재시도 폭풍, 죽은 endpoint가 큐를 점유하는 문제 |
| DLQ + 수동 재배달 | 최종 실패를 DLQ로, 운영자/테넌트가 재배달 트리거 | DLQ 폭증 관리, 재배달 시 순서·중복 |
| 자동 비활성화 | 연속 실패 endpoint 자동 disable + 통지 | 서킷 브레이커 상태 전이, 복구 반개방(half-open) |
| 배달 이력 조회 | 시도별 상태·응답코드·소요시간 (커서) | 대량 이력 파티셔닝/정리 정책 |
| 테넌트별 제한 | rate limit + 동시 배달 수 제한 | **noisy neighbor 격리** — 멀티테넌시의 본질 문제 |
| 관측 대시보드 | 성공률·지연 히스토그램·큐 적체 (Grafana) | 메트릭 설계(RED), 카디널리티 폭발 주의 |

의도적으로 뺀 것: 이벤트 변환(transformation)·필터 DSL·웹 UI — 배달 신뢰성이라는 코어에 집중. 수신 확인용 데모 수신 서버(`/demo-receiver`)는 별도 경량 앱으로 포함(E2E와 시연에 사용).

## 3. 기술 스택

| 구분 | 선택 | 이유 |
|------|------|------|
| 언어/프레임워크 | TypeScript 5 (strict), NestJS 11 | 서브 스택 유지·심화. API와 Worker를 같은 코드베이스에서 프로세스만 분리 |
| ORM | Prisma | Todayskin 경험 재사용 — 도구 학습 비용 최소화, 도메인에 시간 투자 |
| DB | PostgreSQL 16 | 이벤트·배달 이력의 영속 저장, outbox 테이블 |
| 큐 | **BullMQ (Redis 7 기반)** | 재시도·백오프·지연 잡·DLQ·동시성 제한이 내장 — 이 프로젝트의 요구와 정확히 일치 |
| HTTP 클라이언트 | undici | 타임아웃·커넥션 풀 제어 명시적 |
| 모니터링 | Prometheus + Grafana, pino 구조화 로그 | 인프라 지향 역량의 증거물. 로그-메트릭-대시보드 3종 |
| 부하테스트 | k6 | 발행 RPS vs 배달 지연 곡선 |
| 인프라 | Docker Compose(api·worker·redis·pg·prom·grafana·demo-receiver), GitHub Actions, EC2 | 컨테이너 7개짜리 compose를 혼자 운영하는 경험 자체가 산출물 |

### 왜 Kafka가 아니라 BullMQ인가 (기획 단계 트레이드오프 — 면접 단골)

| 기준 | BullMQ(채택) | Kafka |
|------|--------------|-------|
| 요구 패턴 | 잡 큐(개별 잡 재시도·지연·DLQ) — **정확히 일치** | 스트림(파티션 순서·리플레이·다중 컨슈머 그룹) |
| 개별 잡 재시도/백오프 | 내장 | 직접 구현(재시도 토픽 체인 등) — 복잡 |
| 운영 부담 | Redis 하나 | 브로커·주키퍼(KRaft)·파티션 운영 |
| 이 규모 적합성 | 적정 | 오버엔지니어링 |

→ "웹훅 배달은 per-job 제어가 필요한 잡 큐 문제고, 이벤트 리플레이·다중 소비자가 필요해지면(감사 파이프라인 등) 그때 Kafka를 **추가**한다"가 답변. Kafka 개념(파티션·오프셋·컨슈머 그룹)은 README의 확장 설계 섹션에 문서로 정리해 학습을 증명한다.

### 클라이언트 결정 — 웹 vs 앱

| 후보 | 판단 |
|------|------|
| 모바일 앱 | 탈락 — 사용자가 "개발자(데스크에서 연동 작업)"라 모바일 시나리오 없음 |
| **웹 개발자 콘솔 (채택)** | Stripe·GitHub의 webhook 설정 화면이 전부 웹 콘솔인 것과 같은 이유. 특히 **라이브 데모 페이지** — 왼쪽에서 이벤트를 발행하면 오른쪽에 demo-receiver 수신 로그가 실시간으로 찍히는 화면 — 가 비동기 배달 파이프라인 전체를 한 화면에 시각화한다 (GitHub 소개 GIF로 최적) |

- 스택: Vite + React + TypeScript(strict). 화면 5개 — API 키 발급(원문 1회 노출 UX) · endpoint 등록(+SSRF 거부 에러 표시) · 배달 이력 테이블(상태 필터 + 시도 타임라인 펼침) · DLQ 목록 + 재배달 버튼 · **라이브 데모(SSE로 수신 로그 스트리밍)**
- 역할 구분: 콘솔 = 테넌트 셀프서비스 / Grafana = 운영자 관측 — 두 화면의 목적이 다름
- 원칙: 프론트는 유리창 — AI 도구로 빠르게 생성, 전체 시간의 15% 상한

### Git·주석 전략 (커밋·푸시·PR·코드 주석) — 백엔드와 프론트를 다르게

> 원칙: **백엔드는 공부의 기록, 프론트는 결과물만.** 실패 시나리오의 "재현 스크립트 → 방어 코드 → 검증 테스트" 3점 세트가 커밋·PR의 기본 단위다.

| 구분 | 백엔드 (학습의 본체) | 프론트엔드 (거들 뿐) |
|------|---------------------|---------------------|
| 커밋 | **1커밋 = 1개념**, scope로 컴포넌트 구분 — `feat(relay): outbox 폴러 원자적 마킹`, `feat(worker): 지수 백오프+풀 지터`, `test(chaos): redis kill 중 무유실 재현` | 화면 단위 뭉텅이 허용 — `fe: 배달 이력 테이블` (AI 생성 코드 그대로 OK). demo-receiver도 프론트급으로 취급 |
| 브랜치 | GitHub Flow. 핵심 문제(§7) 1개 = 브랜치 1개 — `feat/outbox-relay`, `feat/circuit-breaker`, `feat/tenant-isolation` | `fe/console` 브랜치 하나로 진행 |
| PR | **혼자여도 PR을 연다** — 본문에 3점 세트와 카오스 테스트 결과(전/후 p95) 기록, CI 초록 없이 머지 금지 | 생략 가능(main 직행) 또는 1개 — 라이브 데모 GIF 한 장이면 충분, squash 머지 |
| PR 단위 | 핵심 문제 1개 = PR 1개 — "격리 전후 수치"가 담긴 PR이 포트폴리오의 킬러 콘텐츠 | 프로젝트 전체에서 PR 1개 |
| 푸시 | 매일 푸시, main force push 금지 | 동일 |
| 이력 관리 | 격리 전(문제 재현) 상태를 태그로 보존 (`v0-no-isolation`) → 부하 비교의 기준점 | 이력 가치 없음 |

**주석 규칙 — 코드가 곧 교재가 되도록:**

- **백엔드: 핵심 로직마다 설명 주석 필수.** "무엇을 하는지"가 아니라 **왜 이 방식인지**(문제 상황 → 대안 → 선택 이유)를 적는다. 예 — outbox 폴러 위에: `// DB 커밋과 큐 발행은 하나의 트랜잭션으로 묶을 수 없다(이중 쓰기 문제) → 이벤트를 같은 트랜잭션으로 outbox 테이블에 기록하고 폴러가 발행. 발행은 at-least-once이므로 중복 방어는 수신측 멱등성이 담당`. 재시도·백오프·ack 시점 등 신뢰성 결정마다 이유를 남긴다.
- **프론트·demo-receiver: 주석 최소.** AI가 생성한 콘솔 코드 그대로 두고, 백엔드 계약과 닿는 지점(HMAC 서명 검증 예제, 재배달 버튼의 멱등성 안내)에만 한 줄 남긴다.

## 4. 아키텍처

```
[테넌트 서비스 / 웹 콘솔(frontend/)]             [수신자 Endpoint (외부)]
      │ POST /events (API Key + Idempotency-Key)          ▲
      ▼                                                   │ POST (HMAC 서명, 타임아웃 10s)
[API Server — NestJS]                             [Worker — NestJS (별도 프로세스, N대 수평 확장)]
      │ 같은 트랜잭션:                                     ▲
      │  events INSERT + outbox INSERT                    │ 잡 소비 (테넌트별 동시성 제한)
      ▼                                                   │
[PostgreSQL] ──> [Outbox Relay (폴러, 500ms)] ──> [Redis / BullMQ]
  · events            · 미발행 outbox 행을        · delivery 큐 (attempt 잡)
  · endpoints           큐에 적재 후 마킹          · 지연 잡 = 재시도 백오프
  · deliveries        · at-least-once 보장        · DLQ (최종 실패)
  · delivery_attempts
      ▲                                           [서킷 브레이커 상태] (Redis)
      └── Worker가 시도 결과를 기록                 · endpoint별 연속 실패 카운트

[Prometheus] ◄─ /metrics (api, worker, relay)     [Grafana] 대시보드
[pino 로그] ─ delivery_id 단위 상관관계 추적 (correlation id)
```

**컴포넌트 역할:**
- **API Server** — 발행 수신·검증·영속화. 큐를 직접 만지지 않는다(outbox에만 쓴다).
- **Outbox Relay** — DB의 outbox를 폴링해 BullMQ에 적재. "DB 커밋 = 배달 예약 확정"을 보장하는 다리.
- **Worker** — 잡을 소비해 실제 HTTP 배달. 결과 기록, 실패 분류, 재시도 스케줄, 서킷 갱신. **수평 확장 대상.**
- **PostgreSQL** — 진실의 원천(무엇을 배달해야 했고, 무엇이 일어났나). **Redis가 전소해도 outbox에서 복원 가능.**

## 5. 데이터베이스 설계

### tenants / api_keys
- tenants: id PK, name, plan('FREE'/'PRO' — rate limit 차등), status
- api_keys: id PK, tenant_id FK, **key_hash** VARCHAR UNIQUE (SHA-256, 원문 미저장 — 발급 시 1회만 노출), last4, status('ACTIVE'/'GRACE'/'REVOKED'), expires_at
  - 키 회전: 새 키 발급 시 구 키는 GRACE(24h) → 자동 REVOKED. 인덱스 `(key_hash) WHERE status != 'REVOKED'`

### endpoints — 수신 지점
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID PK | |
| tenant_id | FK→tenants | 인덱스 |
| url | VARCHAR(500) | 등록 시 SSRF 검증 통과 필수 |
| secret | VARCHAR | HMAC 서명용 (암호화 저장 — AES-GCM, 앱 레벨) |
| status | VARCHAR | 'ACTIVE' / 'DISABLED_AUTO'(서킷) / 'DISABLED_MANUAL' |
| consecutive_failures | INT | 자동 비활성 판단용 |
| | | UNIQUE(tenant_id, url) |

### subscriptions — endpoint가 구독한 이벤트 타입
- endpoint_id FK, event_type VARCHAR('order.created' 등 점 표기), **UNIQUE(endpoint_id, event_type)**

### events — 발행된 이벤트 (불변)
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID PK | 수신자에게도 노출되는 배달 멱등성의 근거 |
| tenant_id | FK | 인덱스 `(tenant_id, created_at DESC)` |
| type | VARCHAR(100) | |
| payload | JSONB | 최대 64KB 제한 |
| idempotency_key | VARCHAR | **UNIQUE(tenant_id, idempotency_key)** — 발행 중복 차단 |
| created_at | TIMESTAMPTZ | |

### outbox — 발행-적재 원자성의 핵심
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | BIGSERIAL PK | 처리 순서 |
| event_id | UUID FK | |
| status | VARCHAR | 'PENDING' / 'PUBLISHED' |
| published_at | TIMESTAMPTZ NULL | |
| | | 부분 인덱스 `(id) WHERE status='PENDING'` — 폴러 스캔 비용 최소화 |

### deliveries — 이벤트×endpoint 배달 단위
| 컬럼 | 타입 | 설명 |
|------|------|------|
| id | UUID PK | 수신자에게 `X-Delivery-Id`로 전달 — **소비자 멱등성 키** |
| event_id / endpoint_id | FK | UNIQUE(event_id, endpoint_id) — 팬아웃 중복 생성 차단 |
| status | VARCHAR | 'PENDING' / 'SUCCEEDED' / 'FAILED_RETRYING' / 'DEAD' |
| attempt_count | INT | |
| next_retry_at | TIMESTAMPTZ | 조회용 (실제 스케줄은 BullMQ 지연 잡) |

### delivery_attempts — 시도 이력 (불변, 시도당 1행)
- id PK, delivery_id FK(인덱스), attempt_no, request_headers_digest, response_status INT NULL, response_body_head VARCHAR(1KB 절단), error_class('TIMEOUT'/'CONN_REFUSED'/'HTTP_4XX'/'HTTP_5XX'), duration_ms, attempted_at
- **정리 정책:** 90일 경과 행 삭제 배치(또는 월별 파티셔닝 실험) — "이력 테이블은 무한히 자란다"에 대한 답을 설계에 포함

## 6. API 설계

인증: 테넌트 API는 `Authorization: Bearer sk_live_...` (API Key) / 데모 편의상 관리자는 별도 admin 키

| Method | Endpoint | 인증 | 설명 |
|--------|----------|------|------|
| POST | /tenants | admin | 테넌트 생성 + 첫 API 키 발급 |

| PUT | /endpoints/{id}/subscriptions | 🔑 | 구독 타입 일괄 설정 |
| POST | /events | 🔑 + IdemKey | **이벤트 발행** — 202 Accepted |
| GET | /events/{id}/deliveries | 🔑 | 이벤트의 배달 현황 |
| GET | /deliveries?status=DEAD&cursor= | 🔑 | 배달 목록 (DLQ 필터) |

| POST | /deliveries/{id}/redeliver | 🔑 | **수동 재배달** (DEAD/SUCCEEDED 모두 허용 — 수신자 디버깅용) |
| POST | /endpoints/{id}/ping | 🔑 | 테스트 이벤트 발송 (연동 개발용) |
| GET | /metrics | 내부망 | Prometheus 스크레이프 |

**대표 API 상세 — POST /events**

```json
{ "type": "order.created", "payload": { "orderId": "ord-1", "amount": 12000 } }
```
응답 202: `{ "eventId": "uuid", "deliveries": [{ "deliveryId": "uuid", "endpointId": "uuid" }] }`
- 202인 이유: 배달은 비동기 — "접수 완료"와 "배달 완료"는 다른 사건. 완료 확인은 조회 API로.
- 에러: `409 DUPLICATE_EVENT`(멱등 키 중복 — 기존 eventId 반환), `413 PAYLOAD_TOO_LARGE`, `429 RATE_LIMITED`(Retry-After 포함)

**배달 요청 규격 (수신자가 받는 것) — 이 자체가 공개 API 문서가 된다:**
```
POST {endpoint.url}
X-HookRelay-Event: order.created
X-Delivery-Id: {uuid}            ← 수신자 멱등 처리 기준
X-HookRelay-Timestamp: 1755075600
X-HookRelay-Signature: v1=hex(HMAC-SHA256(secret, timestamp + "." + body))
```
2xx 응답 = 성공, 그 외/10초 타임아웃 = 실패로 분류.

## 7. 핵심 백엔드 문제 (문제→원인→해결→선택 이유→비교→트레이드오프)

### 문제 1. 발행-적재 원자성 — "DB엔 있는데 큐엔 없는" 이벤트

- **문제:** `events INSERT 커밋 → 큐 적재` 사이에 프로세스가 죽으면 그 이벤트는 영원히 배달되지 않는다. 순서를 바꾸면(큐 먼저) DB에 없는 유령 이벤트가 배달된다.
- **원인:** DB와 Redis는 서로 다른 시스템 — 둘을 하나의 트랜잭션으로 묶을 수 없다(분산 트랜잭션의 부재).
- **해결(채택): Transactional Outbox** — events와 outbox를 **같은 DB 트랜잭션**으로 INSERT. 별도 Relay가 PENDING outbox를 폴링(500ms)해 큐 적재 후 PUBLISHED 마킹. 적재 후 마킹 전에 죽으면 재적재되므로 **중복은 가능, 유실은 불가능** = at-least-once.
- **왜:** "유실 vs 중복" 중 무엇을 감수할지 정하는 문제 — 웹훅은 중복을 감수하고(멱등 소비로 해결) 유실을 막는 것이 업계 표준.
- **비교:** ① 큐만 신뢰(BullMQ 직접 적재): Redis 유실(재시작·페일오버) 시 근거 없음 ② 2PC: PostgreSQL-Redis 간 불가·비현실 ③ CDC(Debezium): outbox의 정석 확장판이나 인프라 과함 — "폴링→CDC" 발전 경로로 문서화.
- **트레이드오프:** 폴링 지연(≤500ms)과 DB 부하. 부분 인덱스로 스캔 비용을 고정하고, 폴링 주기 vs 지연 곡선을 실험 수치로 남긴다.

### 문제 2. 재시도 설계 — 백오프, 그리고 재시도 폭풍

- **문제:** 수신자가 30분 다운되면 그동안의 실패를 언제 다시 보낼 것인가? 복구 순간 밀린 재시도가 한꺼번에 몰리면(thundering herd) 갓 살아난 서버를 다시 죽인다.
- **원인:** 고정 간격 재시도는 장애 지속시간과 무관하게 부하를 반복하고, 동기화된 재시도는 스파이크를 만든다.
- **해결(채택):** 지수 백오프 + **풀 지터**: `delay = random(0, min(cap, base × 2^attempt))`, base 30s, cap 4h, 최대 8회(누적 약 13h) → 이후 DEAD(DLQ). BullMQ 커스텀 backoffStrategy로 구현.
- **왜:** 지수는 장애 길이에 적응하고, 지터는 재시도 시각을 분산시킨다(AWS Architecture Blog의 표준 권고).
- **비교:** 고정 간격(단순하나 스파이크), 지터 없는 지수(2^n 시각 동기화 스파이크 여전), equal jitter vs full jitter(실험으로 분포 비교 — 그래프를 README에).
- **트레이드오프:** full jitter는 개별 배달의 지연 예측이 어렵다 → next_retry_at을 기록해 조회 API로 노출, 최대 지연 SLA(예: "실패 시 최대 13시간 내 8회 시도")를 문서 계약으로.

### 문제 3. Noisy Neighbor — 죽은 endpoint 하나가 전체를 마비

- **문제:** 테넌트 A의 endpoint가 10초 타임아웃으로 죽어 있으면, 워커 동시성 10이 전부 A 대기에 묶여 테넌트 B의 정상 배달까지 지연된다.
- **원인:** 공유 큐 + 공유 워커 풀에서 느린 잡이 처리 슬롯을 점유 — 멀티테넌시의 본질적 격리 문제.
- **해결(채택): 2중 격리** — ① **BullMQ Group(테넌트별 그룹 동시성 제한)**: 테넌트당 최대 동시 배달 3으로 상한 ② **endpoint 서킷 브레이커**: 연속 실패 10회 → OPEN(즉시 실패 처리, HTTP 시도 생략) → 5분 후 HALF_OPEN(1건만 시도) → 성공 시 CLOSE. 연속 실패 50회면 endpoint 자동 DISABLED_AUTO + 테넌트 통지.
- **왜:** 그룹 제한은 "점유율"을, 서킷은 "무의미한 시도 자체"를 차단 — 층위가 다른 두 방어.
- **비교:** 테넌트별 큐 분리(격리 완벽하나 큐 수백 개 운영·워커 배분 복잡), 우선순위 큐(기아 문제). 그룹 동시성이 운영 단순성과 격리의 균형점.
- **트레이드오프:** 서킷 OPEN 중 이벤트는 시도 없이 실패 처리되므로 재시도 스케줄로 넘긴다 — "빨리 실패하고 나중에 재시도"가 "느리게 전부 시도"보다 시스템 전체에 이롭다는 판단을 수치(격리 전/후 p95)로 증명.

### 문제 4. 중복 배달과 소비자 멱등성 — exactly-once의 진실

- **문제:** outbox 재적재, 워커 크래시(시도 후 기록 전 사망), 수동 재배달 — 같은 이벤트가 수신자에게 2번 도착할 수 있다.
- **원인:** at-least-once 시스템에서 중복은 버그가 아니라 **명세**다. exactly-once 배달은 일반 HTTP 수신자에 대해 이론적으로 불가능(승인 유실 문제).
- **해결(채택):** ① 우리가 줄 수 있는 것: 안정적인 `X-Delivery-Id`(같은 배달의 재시도는 같은 ID) + 문서로 "이 ID로 멱등 처리하라" 계약 명시 ② demo-receiver에 processed_delivery_ids 테이블로 멱등 소비 **모범 구현을 직접 제공** ③ 워커 내부: attempt 기록을 시도 전 INSERT(claim) → 결과 UPDATE로, 크래시 시 중복 시도를 이력에서 식별 가능하게.
- **왜:** "중복을 없앤다"가 아니라 "중복을 안전하게 만든다"가 올바른 문제 정의 — 이 재정의 자체가 면접에서 급을 가른다.
- **비교:** 배달 전 dedup 캐시(Redis SETNX)로 중복을 줄일 수는 있으나(best-effort) 보장은 못 함 — 줄이기(우리) + 견디기(수신자) 이중 구조가 정답.
- **트레이드오프:** 수신자에게 구현 부담 전가 — 그래서 Stripe도 GitHub도 문서로 요구한다. 우리는 데모 코드까지 준다.

### 문제 5. SSRF — 웹훅 서비스는 "서버가 임의 URL로 요청을 보내주는 서비스"다

- **문제:** 공격자가 endpoint로 `http://169.254.169.254/latest/meta-data`(EC2 메타데이터)나 `http://10.0.0.5:6379`를 등록하면, 우리 워커가 내부망을 대신 찔러주는 프록시가 된다.
- **원인:** 사용자 입력(URL)으로 서버가 아웃바운드 요청을 수행하는 구조 자체 — 웹훅 서비스의 태생적 공격면.
- **해결(채택): 3중 방어** — ① 등록 시: https 강제(데모 http 허용 플래그), DNS 해석 후 사설·루프백·링크로컬 대역(RFC1918, 169.254/16, ::1 등) 차단 ② **배달 시마다 재검증**: 커스텀 undici Agent의 connect 단계에서 해석된 실제 IP를 검사 — **DNS rebinding**(등록 땐 공인 IP, 배달 땐 내부 IP로 바꾸는 공격) 차단 ③ 워커 네트워크 최소 권한(컨테이너에서 내부 서비스로의 라우트 차단, 클라우드에선 SG 아웃바운드 정책).
- **왜:** 등록 시 1회 검증만 하는 흔한 구현의 구멍(rebinding)까지 막는 것이 차별점.
- **비교:** 아웃바운드 전용 프록시(Smokescreen 같은 egress proxy)가 대기업 정석 — 발전 경로로 문서화.
- **트레이드오프:** connect 훅 검증은 배달마다 소액의 오버헤드 — 보안이 우선하는 지점임을 명시.

## 10. 장애 대응

| # | 장애 | 대응 설계 |
|---|------|-----------|
| 1 | **Redis(큐) 전면 다운** | 발행 API는 계속 동작(outbox까지만 쓰므로) — **수신 무중단**. Relay가 적재 실패를 재시도하며 대기, Redis 복구 시 PENDING부터 자동 재개. "큐가 죽어도 이벤트는 안 잃는다"를 카오스 테스트(redis kill 5분)로 시연 |
| 2 | **워커 전멸/크래시** | 큐에 잡이 적체될 뿐 유실 없음. BullMQ stalled 감지로 처리 중이던 잡 재할당. 적체 깊이 메트릭 알람(Grafana) |
| 3 | **수신자 대규모 장애** (여러 endpoint 동시 다운) | 서킷+백오프로 시도량 자동 감쇠, DLQ 적재 → 복구 후 일괄 재배달 API. 재배달 시 rate 제한으로 2차 폭주 방지 |
| 4 | **DB 다운** | 유일한 전면 장애점 — 발행 5xx(호출자 재시도+멱등 키로 안전), 워커는 기록 실패 시 잡 재시도. RDS 다중 AZ가 정답임을 문서화 |
| 5 | Relay 이중 실행 (배포 겹침) | outbox 마킹을 `UPDATE ... WHERE status='PENDING' RETURNING`으로 원자화 — 중복 적재가 나도 at-least-once 명세 안 |
| 6 | attempts 테이블 폭증 | 90일 정리 배치 + 테이블 크기 메트릭 — "용량도 장애다" |

각 장애는 재현 스크립트(`docs/chaos/`)와 사후 리포트 양식으로 남긴다. **Grafana 대시보드에 "장애 주입 중" 스크린샷을 포함**하는 것이 포트폴리오 차별점.

## 12. 배포

```
GitHub Actions: lint+test → docker build (api/worker 동일 이미지, CMD만 분리) → GHCR
→ EC2: docker compose up (nginx, api×1, worker×2, redis, postgres 또는 RDS, prometheus, grafana, demo-receiver)
· 웹 콘솔: nginx가 frontend/ 빌드를 정적 서빙 (API와 같은 도메인 — CORS 단순화)
· Grafana 대시보드 JSON을 레포에 커밋(provisioning) — "클론하면 대시보드까지 재현"
· 워커만 scale: docker compose up -d --scale worker=3
```
발전 경로 문서화: compose→ECS(서비스 분리)→(학습용) K8s HPA로 워커 오토스케일 — 인프라 지향 로드맵(v4·K8s 학습)과 접속점.

## 14. 학습 가이드 — 코드를 하나씩 보며 공부하는 법

**규칙: 실패 시나리오마다 "재현 스크립트 → 방어 코드 → 검증 테스트" 3점 세트로 커밋.**

| 3 | HTTP 클라이언트 타임아웃 계층(connect/headers/body), HMAC | "타임아웃 10초의 근거는? 30초면 뭐가 나빠지나?" |

**코드 읽기 순서:** ① prisma/schema(outbox·deliveries가 왜 분리인가) ② 발행 트랜잭션 ③ relay 루프 ④ 워커 프로세서(실패 분류) ⑤ 백오프 전략 ⑥ 서킷 ⑦ metrics 모듈.
**블로그 소재:** outbox 없이 이벤트를 잃어버리는 과정 재현 / 지터 유무 재시도 분포 시각화 / noisy neighbor 격리 전후 p95 / 웹훅 서비스의 SSRF — DNS rebinding까지.

## 15. 이 프로젝트로 증명할 수 있는 역량

- 메시지 큐·비동기 파이프라인·배달 보장 — **"응답 이후"를 설계하는 능력** (신입 CRUD 포트폴리오와 결정적 차별)
- at-least-once/멱등성/outbox 등 분산 시스템 어휘의 실전 구사
- 멀티테넌트 격리·서킷 브레이커 등 장애 **격리** 설계
- SSRF·HMAC·리플레이 방지 — 공격면 관점의 보안 사고
- Prometheus/Grafana 관측 구축 — 인프라·SRE 지향의 실증 (커리어 방향과 직결)
- TS/NestJS 실무 수준 유지 (스타트업·글로벌 풀 보험)

## 16. 면접 예상 질문 (12)

1. outbox 패턴이 해결하는 문제를 "두 시스템, 한 트랜잭션"의 관점에서 설명하라. relay가 죽으면 어떻게 되나?
2. exactly-once 배달이 불가능한 이유는? 그럼 무엇을 보장하고 무엇을 요구했나?
3. 재시도에 지터를 넣는 이유를 복구 직후 상황으로 설명하라. full jitter와 equal jitter의 차이는?
4. 느린 endpoint 하나가 다른 테넌트에 주는 영향을 어떻게 측정했고 어떻게 격리했나?
5. 서킷 브레이커의 상태 전이와 각 임계값(10회/5분/50회)의 근거는?
6. 워커를 3대로 늘리면 같은 잡이 두 번 실행될 수 있나? BullMQ의 stalled 처리와 함께 설명하라.
7. HMAC 서명에 timestamp를 포함한 이유는? 수신자가 서명 검증을 안 하면 어떤 공격이 가능한가?
8. DNS rebinding 공격 시나리오와 connect 단계 검증으로 막는 원리를 설명하라.
9. Redis가 5분간 죽었다 살아났다 — 그 사이 발행된 이벤트의 운명을 시간 순으로 설명하라.
10. Kafka를 안 쓴 이유와, Kafka가 필요해지는 요구사항 변화는 구체적으로 무엇인가?
11. 배달 성공률 지표가 갑자기 떨어졌다 — 대시보드에서 어떤 순서로 원인을 좁히나? (큐 적체? 특정 endpoint? 전체 네트워크?)
12. attempts 이력이 수억 건이 되면 어떤 문제가 생기고, 파티셔닝과 삭제 배치 중 무엇을 왜 택하겠나?
